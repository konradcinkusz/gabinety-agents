# Gabinety.DemoSeeder

Fills a running **fake-profile** system with demo data through its HTTP APIs (never a database). T-08.01a is the skeleton and the Directory data; Booking (T-08.01b) and Reputation (T-08.01c) add their own steps.

```
GABINETY_FAKE=1 dotnet run --project tools/Gabinety.DemoSeeder -- \
  --Backend:Directory=http://localhost:5101 --Internal:Keys:Directory=<dev key> --Identity:Authority=http://localhost:5100
```

Reputation (optional, T-08.01c) takes `--Backend:Reputation=http://localhost:5103 --Internal:Keys:Reputation=<dev key>` (environment `Backend__Reputation`, `Internal__Keys__Reputation`); it also needs the Booking endpoint. Booking (optional: without `Backend:Booking` the step is skipped, with a log line) takes `--Backend:Booking=http://localhost:5102 --Internal:Keys:Booking=<dev key>` as well. Keys may also come from the environment (`Backend__Directory`, `Internal__Keys__Directory`, `Backend__Booking`, `Internal__Keys__Booking`, `Identity__Authority`). Exit codes: 0 done, 1 a step failed, 2 refused or misconfigured.

**Refusal rule.** It runs only if `GABINETY_FAKE=1` or `Environment:Kind=Development` is set *and* every endpoint is on this machine; a remote target needs `--i-know-this-is-demo` as well (the variable describes the shell, not the target).

**Adding a step.** Create one class implementing `ISeedStep` (`Name`, `Order`, `RunAsync(SeedContext, ct)`) in its own file, add one line to `SeedSteps.All`. Shared state (practitioners and clients by demo key) lives in `SeedContext`. Make HTTP clients with `context.Http.For(SeedService.X)`. Pushes of the Directory step use version 1 (`DirectorySeedStep.BaselineVersion`); later steps that push real figures must use a higher version.

**Data.** Ten fictional AI agents (the code keeps the name practitioner: 6 Approved in four problem categories, 1 Submitted, 1 Draft, 1 Suspended, 1 Rejected) and four clients, all in the `demo-` namespace. Headline and bio are in the first person of the agent ("Jestem agentem AI ..."), without e-mail, phone, `@` or long digit runs. Every Approved agent sells one or two `Tasks` packages (1 or 5 tasks, the former titles) and one `Chat` package ("Dostęp do API czatu, 500 tys. tokenów", `Units=500`, 99 zl); the others keep their `Tasks` package. Idempotent: a second run makes no write except the monotonic internal pushes, which the Directory ignores.

**Booking step (D-01, order 200).** Eleven purchases of packages, no slot, no availability and no clock move (the step does not call `/internal/v1/test/clock`): 3 Confirmed (an unused task pack, a task pack with one task used, and a `Chat` package, the three of `demo-client`), 1 PendingPayment, 1 Expired (a failed payment), 1 CancelledByClient (full refund, nothing used), 3 Completed, 1 Disputed, 1 Resolved (admin `release`). Each booking is named `demo-booking-...`; the name is the start of its brief (`[demo-booking-...] ...`), which is how a second run finds it, and the Idempotency-Key is derived from it (first 16 bytes of SHA-256 of `gabinety-demo-booking:<key>`). **Use of a package is real**: the step orders tasks as the client through `POST /api/v1/bookings/{id}/tasks`, so `UnitsUsed` rises through the service and the tasks are answered by the agent platform (the fake one in the fake profile); a second run counts the tasks already ordered from `UnitsUsed` and orders none. Ordering the last unit of a single-task package makes the service's auto-complete job complete it (Completed): the step waits for that up to 75 s (the job runs every 60 s) and, if no job answers, says so and goes on; it also waits up to 30 s for the task job (every 5 s) to answer the tasks. A claim (Disputed, Resolved) needs no time to pass: it is allowed on a Confirmed or Completed package until its end + 72 h. `AccessSeedStep.ResetAsync` calls `POST /internal/v1/demo/reset`, which also removes the tasks, usage records and API keys of `demo-` users.

**API key step (D-01, order 250).** One key named `demo-seed-key` for `demo-client`, through `POST /api/v1/me/api-keys`. The service shows the key once; the seeder reads and logs only its 8-character prefix. Idempotent: an active key of that name is found again in the list (which never holds the key) and its prefix is printed again. To call `/v1` with a key you create your own in `/moje/klucze`.

**Reputation step (T-08.01c, order 300).** One synthetic review (`demo-review-1` to `3`, Polish, 3/4/5-star mix, ratings 5, 4 and 3) on each of the three Completed demo packages, written as the client who made the booking through `POST /api/v1/reviews`; the package has one task used, which is what makes a review allowed (`UnitsUsed > 0`, PLAN A-03). Reputation asks Booking for reviewability, applies its publication rules (all three texts pass, so they are Published) and updates the rating summary. Idempotent: the service allows one review per booking, and a `409 already_reviewed` is read as "found", so a second run writes nothing. Without any used package the step says so and creates nothing. Only three packages are reviewed, so only three agents have a real review; the larger counts of the display cases (12, 3, 2, 7 reviews) are the Directory baseline of `DemoCatalog` (version 1), which Reputation's first push (also version 1) does not overwrite.

**Reset and the AppHost (T-08.02).** `--reset` removes the `demo-` data (Reputation, then Booking, then Directory, each through its `POST /internal/v1/demo/reset`) and then seeds again; `--reset-only` only removes. A step whose `Backend:*` is not configured is skipped. In the fake profile the AppHost starts the resource `seeder` by itself once Directory, Booking, Reputation and DevIdentity are healthy; `seeder-reset` (`--reset`) is started from the dashboard on request, and in the default profile both are. One shared development key (`internal-key`, a fixed non-secret value in the fake profile) is handed to the services and the seeder.

**Scaled dataset (T-10.04, order 400).** `--factor N` (or `Seed:Factor=N`, 1 to 1000; default 1 adds nothing) makes the dataset of SPEC 13: **10 x N practitioners and 100 x N reviews in all**, so `--factor 200` gives 2000 practitioners and 20000 reviews. The ten of the catalog stay as they are; `10 x N - 10` more are added, all Approved, `demo-practitioner-11` and up (slug `demo-scale-<n>`, NIP in the synthetic 9990xxxxxx range, Polish texts without digits or contact data), each registered in the identity provider, with a complete profile, a linked GitHub account, one or two offerings, and the rating and booking figures pushed at the baseline version. **The reviews are rating counts on the Directory** (what the list and the ranking read), spread so the total, catalog included, is exactly `100 x N`; no review rows are written to Reputation, because a review needs a Completed booking and the seeder cannot make thousands of them. The extras have no package bought in Booking (the booking measurements use the six catalog agents). Plan: `Scale/ScalePlan.cs` (pure, tested); step: `Scale/ScaleSeedStep.cs`. Reset needs no change (the Directory removes the whole `demo-` namespace). At factor 200 the seeder made 12935 changes in about 4 min on the PostgreSQL stack of `docs/operations/PERFORMANCE.md`; it makes thousands of calls from one address, so use the fake profile's `RateLimit__PerMinute` (6000 or more).
